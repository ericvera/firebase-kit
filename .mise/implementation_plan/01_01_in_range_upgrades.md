## Background

`firebase-kit` is a Yarn 4 monorepo (`packageManager: yarn@4.18.0`, `nodeLinker:
node-modules`) publishing three packages from `packages/`:
`firebase-kit-protocol`, `firebase-kit-client`, and `firebase-kit-admin`. Both
dependents declare `firebase-kit-protocol` as `workspace:*`.

This task is the first of a dependency refresh. Nothing has changed yet. Later
tasks merge `firestore-snapshot-utils` into `firebase-kit-admin` (1.2), upgrade
`firebase-admin` across a major boundary (1.3), and move `getsetdel` to 3
(1.4) — **this task must not touch any of those three.** Keeping them separate is
deliberate: it makes any later breakage attributable to a dependency change
rather than to the tooling bumps here.

Version data was read from the npm registry on 2026-08-13.

## Testing suggestions

plus a packed-consumer check, and the packed-consumer check is task 2.1. This

## Gotchas

- **`firebase` and `firebase-functions` each appear twice in one file** — once
  under `devDependencies` and once under `peerDependencies`. Changing only the
  dev copy is the easy mistake here and leaves the published range stale. Grep
  each manifest for the package name after editing and confirm two hits with the
  new version.
- **`eslint` appears in four manifests**, not one. The protocol package is easy
  to forget because it has only three devDependencies.
- **`firebase-tools` is pinned without a caret** (`15.26.0`) in both the root and
  admin manifests. That is deliberate. Do not "normalize" it to `^15.26.0`.
- **A `yarn install` that reports no lockfile change is a legitimate outcome**
  for some of these, since the ranges already resolved to the latest version.
  That is not a failure — the declared floor still moved, which is the point.
- The repo runs `lint-staged` on commit (`*.{ts,tsx,mjs}` → `yarn lint-changed`,
  `*` → `prettier --ignore-unknown --write`), so committing will reformat and
  re-lint. Expect the hook to run and let it.
